HMI AND UI FRAMEWORK

Use LVGL as the primary UI framework.

The HMI hardware is:

Waveshare ESP32-S3-Touch-LCD-7B

The firmware must use:

ESP-IDF
LVGL
ESP32-S3 display driver
ESP32-S3 touch driver

Do not use Arduino GUI libraries.

Do not implement the HMI using raw display drawing unless required by the LVGL display integration.

The LVGL application must be separated from the machine-control application.

ARCHITECTURE

Use the following conceptual architecture:

```
                ┌─────────────────────┐
                │       LVGL UI       │
                │                     │
                │ Home                │
                │ Drying              │
                │ Manual              │
                │ Settings            │
                │ Calibration         │
                │ Alarms              │
                │ History             │
                │ RTC                 │
                └──────────┬──────────┘
                           │
                     HMI Interface
                           │
                ┌──────────▼──────────┐
                │   Machine State    │
                │                     │
                │ Machine Controller  │
                │ Drying Controller   │
                │ Safety Controller   │
                └──────────┬──────────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
       Sensors          Actuators        Storage
          │                │                │
    Temp/RH/ADC       Relays/SSR       SD/NVS/RTC
```

The LVGL UI must never directly control GPIO, Modbus relays, motors, heaters, or other hardware.

For example, do NOT allow:

LVGL Button
↓
relay_set()

Instead:

LVGL Button
↓
HMI command
↓
Machine Controller
↓
Safety validation
↓
Actuator Manager
↓
Relay Controller

This keeps safety logic outside the UI.

LVGL VERSION

Use the LVGL version supported by the selected ESP-IDF environment and Waveshare hardware.

Before implementation:

1. Inspect the existing ESP-IDF project.
2. Identify the installed LVGL version.
3. Identify the Waveshare display driver.
4. Identify the touch controller.
5. Verify the display resolution.
6. Verify the display orientation.
7. Verify RGB/parallel/MIPI/SPI interface details from the actual board documentation.
8. Verify PSRAM configuration.
9. Verify LVGL memory requirements.

Do not assume the display interface or GPIO mapping.

Use the actual Waveshare documentation and existing project configuration.

LVGL TASK

Create a dedicated LVGL task.

Suggested architecture:

lvgl_task
↓
LVGL event handling
↓
UI updates

The LVGL task owns LVGL operations.

Do not call LVGL functions randomly from multiple FreeRTOS tasks.

LVGL is generally not thread-safe.

If another task needs to update the UI:

sensor_task
↓
machine_status
↓
HMI state
↓
LVGL task
↓
UI

Use a queue, event mechanism, shared state with synchronization, or another appropriate mechanism.

Do not allow sensor or machine-control tasks to directly manipulate LVGL objects.

UI UPDATE RATE

Do not update every LVGL object on every sensor reading.

Use an appropriate UI refresh interval.

Suggested starting point:

UI update:
100 to 250 ms

Sensor acquisition and machine-control rates should remain independent from the UI refresh rate.

Example:

Temperature sensor:
1 second

Moisture sensor:
500 ms to 1 second

Machine safety:
Fast periodic task

LVGL:
100 to 250 ms

SD logging:
10 seconds

RTC display:
1 second

Adjust these values based on actual performance testing.

Avoid creating and destroying screens unnecessarily.

Where practical, create screens once and update their contents.

Use LVGL screen loading/navigation mechanisms.

Do not leak LVGL objects when changing screens.

LVGL MEMORY MANAGEMENT

ESP32-S3 PSRAM should be used where appropriate.

Do not blindly allocate large buffers from internal RAM.

Identify:

* LVGL draw buffers
* Display frame buffers
* Image assets
* Font data
* History buffers
* CSV parsing buffers

Measure heap usage.

Avoid unnecessary dynamic allocation during normal machine operation.

Do not continuously allocate/free LVGL objects during the drying process.

Create UI objects during screen initialization and update them.

LVGL THREAD SAFETY

Only the LVGL task should manipulate LVGL objects.

If another FreeRTOS task needs to request a UI action, send a command/event to the LVGL task.

Example:

machine_controller
↓
HMI state update
↓
LVGL task
↓
lv_label_set_text()

Never perform:

lv_label_set_text()

from a sensor task.

Never manipulate LVGL objects from the safety task.

Never manipulate LVGL objects from the data logger task.

TOUCH INTERACTION

Use the Waveshare touch controller supported by the actual hardware.

Support:

* Touch input
* Button press
* Button release
* Slider
* Numeric input
* Keyboard where required

Avoid tiny touch targets.

Use appropriate touch target sizes for a machine HMI.

The interface should remain usable while wearing work gloves where practical.

UI SAFETY

The HMI must not bypass machine safety.

For example:

If the heater is requested ON but a temperature sensor has failed:

HMI:

HEATER
REQUESTED ON

ACTUAL:
OFF

REASON:
TEMPERATURE SENSOR FAULT

The HMI must communicate the reason to the operator.

EMERGENCY STOP

Provide an emergency stop interface if the hardware includes a physical emergency-stop circuit.

Do not rely solely on an LVGL button as the machine's physical emergency stop.

The physical safety circuit should have authority over machine outputs.

If an emergency stop input exists:

Emergency stop active
↓
Safety Manager
↓
Actuators OFF

The HMI displays:

EMERGENCY STOP ACTIVE

DATA FLOW

Use this overall architecture:

```
             ┌────────────────────┐
             │      LVGL HMI      │
             │                    │
             │ Touchscreen        │
             │ Screens            │
             │ Widgets            │
             └─────────┬──────────┘
                       │
                HMI Command Queue
                       │
                       ▼
             ┌────────────────────┐
             │ Machine Controller │
             └─────────┬──────────┘
                       │
                 Safety Manager
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Sensors       Actuators     Storage
          │            │            │
    Temp/RH/ADC   Relay/SSR     SD/NVS/RTC
```

Machine status flows upward:

Sensors
↓
Sensor Manager
↓
Machine Status
↓
HMI State
↓
LVGL

Commands flow downward:

LVGL
↓
HMI Command
↓
Machine Controller
↓
Safety Manager
↓
Actuator Manager
↓
Relay/SSR/Motor

RTC flows to:

RTC
↓
Time Manager
├── HMI clock
├── SD logger
├── Drying history
└── Fault timestamps

MONITORING VS CONTROL

The HMI must clearly distinguish:

Measured values
Setpoints
Requested states
Actual states
Fault states

Example:

Temperature:
48.2 °C

Setpoint:
50.0 °C

Heater:
REQUESTED ON

Heater:
ACTUAL ON

This prevents confusion between operator commands and actual machine behavior.

LVGL DEVELOPMENT PHASE

Add a dedicated HMI development phase after the hardware drivers and machine state model are working.

Recommended sequence:

1. LVGL initialization
2. Display driver
3. Touch driver
4. LVGL task
5. Theme
6. Navigation
7. Home screen
8. Sensor widgets
9. Drying screen
10. Manual control
11. Settings
12. RTC screen
13. Calibration
14. Alarms
15. Drying history
16. System diagnostics
17. Final UI optimization

Do not implement the entire UI before the machine state model exists.

The HMI should consume the machine state model rather than becoming the source of machine logic.

FINAL UI REQUIREMENT

The final HMI should feel like an industrial machine control panel.

Prioritize:

* Large readable values
* Simple navigation
* Clear machine states
* Clear alarms
* Large touch targets
* Minimal unnecessary animation
* Stable screen updates
* Clear actuator status
* Easy manual control
* Easy drying setup
* Easy historical data viewing
* Offline RTC time
* SD card status

Avoid unnecessary UI animations that increase CPU or memory usage.

The machine must remain responsive even while LVGL is updating the display, reading history, or showing drying data.
